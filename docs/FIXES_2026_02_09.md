# Critical Fixes - 2026-02-09

## 1. Native Library Loading (libc++_shared.so)

### Problem
Runtime crash when loading `libllama_jni.so`:
```
dlopen failed: cannot locate symbol "_ZTVNSt6__ndk118basic_stringstreamIcNS_11char_traitsIcEENS_9allocatorIcEEEE" referenced by ... libllama_jni.so
```

### Root Cause
- The native code was compiled with a dependency on `std::stringstream` from the C++ standard library
- The shared C++ library (`libc++_shared.so`) was not being bundled in the APK
- AGP 4.1+ stopped bundling `libc++_shared.so` by default when using `c++_shared` STL

### Solution
Added to `app/build.gradle.kts`:
```kotlin
packaging {
    jniLibs {
        keepDebugSymbols.add("**/libsqlcipher.so")
        keepDebugSymbols.add("**/libllama_jni.so")
    }
    // CRITICAL: Bundle libc++_shared.so for native library compatibility
    pickFirsts.add("**/libc++_shared.so")
}
```

This explicitly picks the shared C++ standard library from the NDK and bundles it into the APK.

## 2. SecretBytes Migration (All 9 Cloud Adapters)

### Problem
API keys were stored as plain strings in memory, vulnerable to memory dumps and long-lived in the heap.

### Solution
1. Moved `SecretBytes` class from `:app` to `:core-contracts` for shared access
2. Extended `ProviderAdapterConfig` with `apiKeySecret: SecretBytes?` field
3. Added `getApiKey()` method that securely retrieves keys with automatic memory wiping
4. Migrated all 9 cloud provider adapters:
   - ✅ OpenAICompatibleAdapter (reference implementation)
   - ✅ AnthropicAdapter
   - ✅ GeminiAdapter
   - ✅ NovitaAdapter
   - ✅ PixAIAdapter
   - ✅ NovelAIAdapter
   - ✅ FluxAdapter
   - ✅ ReplicateAdapter
   - ✅ OllamaCloudAdapter

### Pattern
```kotlin
// Before (insecure)
.header("Authorization", "Bearer ${config.apiKey}")

// After (secure)
val apiKey = config.getApiKey()
    ?: return Result.failure(ProviderException.AuthenticationError())
.header("Authorization", "Bearer $apiKey")
```

## 3. ProviderCrudRepository Race Condition Fix

### Problem
The repository used a hybrid sync/async pattern with fire-and-forget writes:
```kotlin
fun saveSync(provider: Provider) {
    applicationScope.launch(Dispatchers.IO) {
        saveProvider(provider)  // Fire-and-forget!
    }
}
```

This caused race conditions where the UI would read stale data before the async write completed.

### Solution
1. Deprecated all fire-and-forget methods
2. Changed all data modification operations to suspend functions:
   - `saveSync()` → `saveAndAwait()` (suspend)
   - `setProviderEnabled()` → `setProviderEnabledSync()` (suspend)  
   - `updateProviderList()` → `updateProviderListSync()` (suspend)

### Pattern
```kotlin
// Before (fire-and-forget, race condition prone)
fun onProviderToggle(providerId: ProviderId, enabled: Boolean) {
    repository.setProviderEnabled(providerId, enabled)  // Returns immediately, async save
    val providers = repository.listProviders()  // May read stale data!
}

// After (predictable data flow)
fun onProviderToggle(providerId: ProviderId, enabled: Boolean) {
    viewModelScope.launch {
        repository.setProviderEnabledSync(providerId, enabled)  // Suspends until saved
        val providers = repository.listProviders()  // Guaranteed fresh data
    }
}
```
